# Privacy Notes

Jojo's Log is built on a "collect less" principle. This document records what data is and is not collected, and why. It applies to the private rebuild and will inform the public privacy page when a public version launches.

---

## What is collected

### Required to use the app
| Data | Why |
|------|-----|
| Email address | Firebase Auth account; used for login and account recovery only |
| Display label / initials | Appears on care Entries to identify who logged them; required before first log |
| Baby nickname | Identifies whose log you are viewing; no legal name required |

### Optional
| Data | Why |
|------|-----|
| Baby birthdate | Used only to show baby age in weeks inside the app; never shared |

### Generated by use
| Data | Why |
|------|-----|
| Care Entries (time, amount, diaper, vitd, medication, notes) | Core product data; family-scoped |
| `createdByLabel`, `updatedByLabel` | Audit trail within the family |
| `createdAt`, `updatedAt`, `deletedAt` | Timestamps for audit and sync |
| Weekly Usual Bottle Amount | Manually entered by an Owner; family-scoped |

---

## What is NOT collected

- Child full legal name
- Parent full legal name
- Address (home or otherwise)
- Health card number
- Precise GPS location
- Photos
- Contact list
- Doctor name
- Medical diagnosis
- Growth measurements (weight, length, head circumference)
- Sleep data
- Event-level analytics on baby care (no "session started", "entry logged" analytics)

---

## Notes field

Parents type freely in the Notes field. The app does not parse, analyse, or act on note content. However, the app is not end-to-end encrypted; notes are stored in Firestore and visible to Firebase. The Help section should include gentle guidance:

> "Avoid entering health card numbers, addresses, or sensitive medical details in notes."

This guidance is informational only. It is not a restriction.

---

## No medical use

The app is not a medical device. It gives no medical advice, dosage guidance, growth interpretation, or clinical recommendations. No content in the app should be construed as medical guidance. The app is a care ledger.

---

## No ads, no data selling

The app has no ads. User data is never sold, shared with advertisers, or used for targeting. The donation model means there is no commercial incentive to monetise user data.

---

## No analytics on care events

Aggregate, anonymous, event-level analytics on baby care events (e.g. "user logged 4 entries today") are not used. Basic Vercel/Firebase platform-level telemetry may be present (page load counts, function calls) but is not tied to baby-level data.

---

## Data residency

Data is stored in Firebase/Firestore (Google). The private app uses a Firebase project in whatever region is configured. For the public app, the Firebase region should be documented in the privacy page.

---

## Data access within the family

Within a Family, all Members (Owners and Caregivers) can see all Entries for all active Babies. There is no per-Member privacy within the shared workspace. This is intentional: the whole point is that every caregiver knows what happened.

---

## Data export and deletion

### Export
Owners can export a CSV of the active Baby's history at any time. This is not gated.

### Deletion (private)
The founding Owner can contact the developer to request account and family deletion. A formal deletion flow is not built into MVP.

### Deletion (public, future)
Before public launch:
- A contact email for deletion requests must be published on the privacy page
- A self-serve deletion flow should be built or clearly documented
- Deleted family data must be removed from Firestore (not just soft-deleted)

---

## Firebase Auth data

Firebase Auth stores email and authentication tokens. Firebase Auth account deletion is required as part of any full account deletion flow. This is handled by the Firebase Auth admin SDK, not Firestore.

---

## Security rules (current and future)

The current HTML app uses open rules (`allow read, write: if true`). Firebase frontend config is not secret — any browser app exposes it — so open rules mean anyone who discovers the Firebase project ID can read or write the `feeds` collection. This is a **deliberate, time-limited risk** accepted for a private prototype used only by two people with no public link sharing. It is not a general-purpose justification and must not carry over to the Vue rebuild or the public app.

The Vue app's Firestore rules must enforce family-scoped access before it is used by anyone outside the household, and absolutely before any public launch. Specifically:
- User must be signed in
- User can only access a Family where `members/{uid}` exists and `active === true`
- Owners can manage members, babies, invite codes, family settings, and restore deleted Entries
- Caregivers can create Entries and edit/delete only their own Entries
- No client-side write of `createdByUserId` to a UID other than the signed-in user's own
- `feeds` collection: locked to read-only after HTML app is retired

New restrictive rules must not be applied until the HTML app is no longer in use, because tightening rules prematurely would break the production app.

---

## Public launch checklist (privacy-specific)

Before the app is offered to the public:

- [ ] Separate Firebase project (no Jojo family data)
- [ ] Firestore security rules fully enforced and reviewed
- [ ] No open global collections
- [ ] No seed data, no personal screenshots in the codebase
- [ ] Public privacy page published (data collected, how it is stored, deletion process)
- [ ] Contact email for deletion requests published
- [ ] Firebase App Check considered for abuse protection
- [ ] No analytics on care events
- [ ] Donation link present but not intrusive
- [ ] No "your baby should" language anywhere in the product
